# Case Study：从评测结果到发布决策

## 目标

为客服 Agent 建立一个跨产品、算法、测试与运营团队都能理解的质量运营框架，解决“评测结果很多，但无法做上线决策”的问题。

## 用户与任务

- AI 产品经理：定义业务指标、版本目标与验收标准。
- 评测 / 测试：构建数据集、Rubric、回归集与 Bad Case 分类。
- 算法工程师：定位检索、Prompt、模型和安全策略问题。
- 平台运营：监控调用、延迟、成本和线上稳定性。

## 指标设计

采用分层指标而非单一总分：

| 层级 | 指标 | 决策作用 |
| --- | --- | --- |
| 业务质量 | 任务完成率、首次解决率 | 判断用户问题是否真正解决 |
| 模型质量 | 事实准确、指令遵循、上下文保持 | 识别能力短板 |
| 风险 | 幻觉率、安全合规率 | 设置上线硬门槛 |
| 工程 | P95 延迟、错误率 | 判断服务稳定性 |
| 经营 | 单次 / 千次会话成本 | 判断规模化可行性 |

## 决策示例

Model B 的质量分数最高，但 P95 延迟与千次成本分别比 Model A 高 77% 与 96%。Model A 已越过质量和安全门槛，因此选择 Model A 进行 10% 灰度，并设置成本告警和 48 小时复盘。

## 迭代闭环

1. 线上与离线样本进入统一评测集；
2. 自动指标筛选后进行高风险人工复核；
3. Bad Case 按检索、Prompt、上下文、安全和产品流程归因；
4. 每个根因关联负责人、修复方式与回归样本；
5. 新版本必须通过发布门禁，灰度后继续监控真实指标。

## 数据声明

本案例所有数字均为模拟数据，目的是展示产品思考、评测框架、数据分析与项目推进方式。
